Secure Spreadsheet Grid - Code Guide

Purpose
- This repo is a browser-first spreadsheet dashboard backed by a Google Apps Script web app.
- The frontend loads the sheet matrix from the Apps Script endpoint, renders it as a native editable table, and writes edits back with `POST { idToken, sheetName, row, col, val }`.
- The spreadsheet remains the source of truth in Google Drive.
- The browser keeps the Google ID token only in memory for the current session.

Latest implementation summary
- The frontend now uses Google Identity Services `credential` tokens instead of the old access-token flow.
- The current Apps Script deployment URL is:
  - `https://script.google.com/macros/s/AKfycbzTC_i2NoYQzN4LdGwAE8ii_t_vznRi2FHqB9783-SHZ8yo7I9BF31SIHFQdig4XKK6/exec`
- `public/app.js` contains the transport adapter:
  - `requestSpreadsheet(method, body)` for request handling
  - `loadMatrixFromSource()` for `GET`
  - `saveCellToSource(row, col, val)` for `POST`
- The frontend now treats Apps Script error objects as blocking responses and only renders the grid after a valid `data` matrix is returned.
- When access is denied, the UI now shows a neutral `Welcome` state and keeps the spreadsheet hidden.

Current user-facing behavior
1. The page opens.
2. `public/index.html` defines `window.APP_CONFIG` and loads Google Identity Services plus the module client.
3. The user signs in with Google and the browser captures the `credential` token.
4. The app sends `GET ?idToken=...&sheetName=...` to the Apps Script web app.
5. The script verifies the token, checks `AllowedUsers`, and returns either:
   - `{ status: "error", message: "..." }` for blocked requests, or
   - `{ currentSheet, allSheets, data }` for allowed requests.
6. If the response includes `data`, the browser renders the matrix into an editable table.
7. If the response is blocked, the browser shows `Welcome` and does not render the grid.
8. When a cell changes, the browser sends `POST { idToken, sheetName, row, col, val }` back to the Apps Script endpoint.
9. The Apps Script deployment writes the new value into the sheet.

Important transport details
- The current Apps Script deployment is expected to expose:
  - `doGet(e)` that returns either an error object or `{ currentSheet, allSheets, data }`
  - `doPost(e)` that accepts JSON in the shape `{ idToken, sheetName, row, col, val }`
- The Apps Script should verify the ID token before any sheet access and should block the `AllowedUsers` sheet from the frontend payload.
- `public/app.js` keeps a future-friendly auth header hook via `forwardAuthToken`, but it is off by default and is not used for the Apps Script route.
- Do not enable the auth header on the Apps Script route unless you are also changing the cross-origin strategy.
- If cross-origin fetches to `script.google.com` are blocked by the host, the frontend will need a same-origin proxy. The UI code is intentionally isolated so that transport can be swapped later without rewriting the grid renderer.

Files and responsibilities
- `public/index.html`
  - Defines `window.APP_CONFIG` with `googleClientId`, `spreadsheetId`, `appsScriptUrl`, and `authScope`.
  - Provides the auth card, dashboard shell, and button labels for the native grid flow.
- `public/app.js`
  - Google Identity Services sign-in bootstrap.
  - In-memory credential token storage.
  - Apps Script GET/POST adapter.
  - Payload normalization, rendering, edit tracking, debounce autosave, and save-error handling.
  - Neutral welcome handling for blocked requests.
- `public/styles.css`
  - Layout for the dashboard, toolbar, table, and detail panel.
  - Cell states for dirty, saving, and error conditions.
- `README.md`
  - User-facing summary of the Apps Script transport and setup.
- `guide.txt`
  - This internal handoff doc for the next AI.
- `.github/workflows/pages.yml`
  - GitHub Pages deployment workflow.
  - Uploads the `public/` directory as the static site artifact on every push to `main`.
- `server.js`
  - Legacy Node backend for the older Sheets API path.
  - Still in the repo, but not required for the current static Apps Script flow.

What changed most recently
- The frontend now shows `Signed in` instead of a longer success notice.
- The denied-access UI now shows a neutral `Welcome` state instead of a denial reason.
- The active Apps Script deployment URL was updated to the latest redeployed endpoint.
- The Apps Script contract now uses real token verification plus an `AllowedUsers` whitelist.
- The frontend now treats Apps Script error objects as blocking responses and does not render the grid when access is denied.

Why the previous approach changed
- The earlier browser-only Google Sheets API path depended on direct spreadsheet permission checks and a lot of auth-state handling that did not match the current Apps Script deployment.
- The current deployment uses the Apps Script web app as the gatekeeper, so the cleanest implementation is to treat that script as the transport layer and make the frontend UI a native grid on top of it.
- This keeps the grid simple, makes the save path explicit, and avoids forcing the app through the wrong permission model.

Session persistence notes
- The browser stores no long-lived Google session in `localStorage` for the current flow.
- The browser keeps the `credential` token in memory only for the active page session.
- Logout clears the in-memory token.
- The spreadsheet data still comes from the live Apps Script endpoint.

Future restricted-mode direction
- If you later switch the Apps Script deployment to a different auth model, keep the auth module separate from the grid renderer.
- The next transport could:
  - forward a bearer token if needed
  - route through a same-origin proxy
  - switch to a backend-backed Google API client
- The current code already isolates the transport in `requestSpreadsheet()`, `loadMatrixFromSource()`, and `saveCellToSource()`.

GitHub Pages deployment notes
- GitHub Pages should be enabled to use GitHub Actions as the source.
- Because this is a project page, the frontend uses relative asset paths instead of root-absolute `/styles.css` and `/app.js`.
- Once Pages is active, the static site can be accessed from anywhere without needing the local Node server.

Testing
- `node --test`
- Browser check:
  - open the static site
  - confirm the grid loads from the Apps Script endpoint for an allowed user
  - edit a cell and confirm the browser posts `{ idToken, sheetName, row, col, val }`
  - sign in with a blocked user and confirm the UI shows `Welcome`
  - confirm the grid does not render for blocked access

If you extend this again
- Keep the transport adapter isolated in `public/app.js`.
- Keep the grid editable even when an individual cell save fails.
- Do not move the app back to the older Sheets API flow unless the product requirement changes.
