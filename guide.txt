Secure Spreadsheet Grid - Code Guide

Purpose
- This app is now a browser-first spreadsheet dashboard backed by a Google Apps Script web app.
- The frontend loads a live matrix from the Apps Script endpoint, renders it as a native editable table, and writes edits back with `POST { row, col, val }`.
- The spreadsheet remains the source of truth in Google Drive.
- The browser still persists Google session state in `localStorage` so the UI can restore after refresh until the token expires.

Latest implementation summary
- The old Google Sheets API direct-read/direct-write flow has been replaced on the frontend.
- The current data source is the Apps Script web app URL in `window.APP_CONFIG.appsScriptUrl`.
- `public/app.js` now contains a small API adapter:
  - `requestSpreadsheet(method, body)` for transport
  - `loadMatrixFromSource()` for `GET`
  - `saveCellToSource(row, col, val)` for `POST`
- The app now renders a full native HTML grid with editable inputs in each cell.
- Changes autosave with a debounce, and save failures are shown inline without logging the user out.
- The signed-in shell now stays visible while the grid loads, so the app does not block rendering behind a sheet-access preflight.

Current user-facing behavior
1. The page opens.
2. `public/index.html` defines `window.APP_CONFIG` and loads Google Identity Services plus the module client.
3. `public/app.js` restores any saved session from `localStorage`.
4. The app immediately requests the Apps Script web app with `GET`.
5. The script returns the sheet as a JSON matrix from the active sheet.
6. The browser renders the matrix into a responsive editable table.
7. Each cell can be edited inline.
8. When a cell changes, the browser sends `POST { row, col, val }` back to the Apps Script endpoint.
9. The Apps Script deployment writes the new value into the sheet.

Important transport details
- The current Apps Script deployment is expected to expose:
  - `doGet(e)` that returns a JSON matrix
  - `doPost(e)` that accepts JSON in the shape `{ row, col, val }`
- The current script in the repo assumes the active sheet in the deployed spreadsheet context.
- `public/app.js` keeps a future-friendly auth header hook via `forwardAuthToken`, but it is off by default.
- Do not enable the auth header unless you are also handling CORS and you actually need it for a future restricted-mode transport.
- If cross-origin fetches to `script.google.com` are blocked by the host, the frontend will need a same-origin proxy. The UI code is intentionally isolated so that transport can be swapped later without rewriting the grid renderer.

Files and responsibilities
- `public/index.html`
  - Defines `window.APP_CONFIG` with `googleClientId`, `spreadsheetId`, `appsScriptUrl`, and `authScope`.
  - Provides the auth card, dashboard shell, and button labels for the native grid flow.
- `public/app.js`
  - Session persistence and Google sign-in bootstrap.
  - Apps Script GET/POST adapter.
  - Matrix normalization, rendering, edit tracking, debounce autosave, and save-error handling.
  - Dashboard shell behavior, row addition, refresh, and error clearing.
- `public/styles.css`
  - Layout for the dashboard, toolbar, table, and detail panel.
  - Cell states for dirty, saving, and error conditions.
- `README.md`
  - User-facing summary of the Apps Script transport and setup.
- `guide.txt`
  - This internal handoff doc for the next AI.
- `.github/workflows/pages.yml`
  - GitHub Pages deployment workflow.
  - Uploads the `public/` directory as the static site artifact on every push to `main`.
- `server.js`
  - Legacy Node backend for the older Sheets-API path.
  - Still in the repo, but not required for the current static Apps Script flow.

What changed most recently
- The guide was rewritten to describe the Apps Script web app architecture instead of the old Sheets API backend path.
- The frontend now exposes the dashboard shell immediately, which means the sheet can load without hiding behind the auth card.
- A `Clear errors` button was wired to clear inline cell-error state instead of accidentally adding a row.
- Toolbar and table styles were updated for the native grid, including sticky row numbers and editable input states.
- The browser runtime was verified to render the sheet data correctly from the Apps Script endpoint.
- A GitHub Pages workflow was added, and the asset paths in `public/index.html` were switched to relative paths so the app works from a GitHub Pages project subpath.

Why the previous approach changed
- The earlier browser-only Google Sheets API path depended on direct spreadsheet permission checks and a lot of auth-state handling that did not match the current Apps Script deployment.
- The user provided a deployed Apps Script web app URL, so the cleanest implementation is to treat that script as the transport layer and make the frontend UI a native grid on top of it.
- This keeps the grid simple, makes the save path explicit, and avoids forcing the app through the wrong permission model.

Session persistence notes
- The browser stores:
  - access token
  - token expiry
  - basic profile information
- These values live in `localStorage` under `native-grid.auth.v1`.
- Logout clears the stored session.
- On refresh, the session restores until the token is close to expiry.
- The stored session is for UI convenience and future restricted-mode compatibility; the live spreadsheet data still comes from the Apps Script endpoint.

Future restricted-mode direction
- If you later switch the Apps Script deployment to restricted mode, keep the auth module separate from the grid renderer.
- The next transport could:
  - forward a bearer token if needed
  - route through a same-origin proxy
  - switch to a backend-backed Google API client
- The current code already isolates the transport in `requestSpreadsheet()`, `loadMatrixFromSource()`, and `saveCellToSource()`.

GitHub Pages deployment notes
- GitHub Pages should be enabled to use GitHub Actions as the source.
- Because this is a project page, the frontend uses relative asset paths instead of root-absolute `/styles.css` and `/app.js`.
- Once Pages is active, the static site can be accessed from anywhere without needing the local Node server.

Testing
- `node --test`
- Browser check:
  - open the static site
  - confirm the grid loads from the Apps Script endpoint
  - edit a cell and confirm the browser posts `{ row, col, val }`
  - refresh and confirm the saved session restores from `localStorage`

If you extend this again
- Keep the transport adapter isolated in `public/app.js`.
- Keep the grid editable even when an individual cell save fails.
- Do not move the app back to the older Sheets API flow unless the product requirement changes.
